# rsvga : architecture

## But

Donner l'accélération 3D DirectX 9 à 11 aux VM Windows sous QEMU/KVM, **sans céder le GPU** (pas de passthrough). Côté Windows, on utilise le **pilote VMware SVGA officiel et signé**, sans mode test ni pilote noyau maison.

## Principe

```
Windows invité  : pilote VMware SVGA officiel (inchangé)
      │  registres, FIFO, command buffers (mémoire partagée)
QEMU (≥ 10.1)   : -device vfio-user-pci,socket=/run/rsvga.sock
      │  protocole vfio-user (socket Unix + mémoire partagée)
rsvga-server    : processus séparé, en Rust (sandbox prévue en M5)
      │  Vulkan (ash)
GPU de l'hôte   : RX 6950 XT, via /dev/dri/renderD*
```

- rsvga implémente la carte **VMware SVGA II** (PCI `15ad:0405`) dans un processus à part. QEMU s'y branche par **vfio-user**, intégré à QEMU depuis la 10.1 : il n'y a pas de gros patch dans QEMU.
- Le rendu se fait **directement en Vulkan**. DXVK n'est pas utilisé, donc l'état graphique n'est pas suivi deux fois comme dans qemu-vmvga.
- La mémoire de l'invité est partagée en memfd (`memory-backend-memfd,share=on`), ce que la VM Tiny11 fait déjà pour virtiofs.

## Composants (crates)

| Crate | Rôle | Jalon |
|---|---|---|
| `svga-proto` | Constantes du protocole VMware, transcrites des en-têtes MIT du *SVGA Device Developer Kit*. `no_std`, sans code. | M0 |
| `svga-core` | Logique pure du périphérique : FIFO, décodage des commandes (2D, objets guest-backed, DX, contextes 3D anciens de Direct3D 9), registres, objets. Sans I/O et sans `unsafe`. | M0 → M3 |
| `svga-shader` | Traducteurs de shaders vers SPIR-V : VGPU10 (bytecode Direct3D SM4/SM5) et Direct3D 9 (SM1 à SM3). Sans `unsafe`. | M3 → M4 |
| `svga-render` | Moteur Vulkan : surfaces sur le GPU de l'hôte, opérations, pipelines. | M3 → M4 |
| `vfio-user` | Protocole vfio-user côté serveur : messages, passage de descripteurs, boucle de requêtes. Sans `unsafe`. | M1 |
| `rsvga-server` | Binaire : config PCI, BAR partagés (memfd scellés), ROM optionnelle, exécution de la FIFO, capture PNG, fenêtre. Seul `shm.rs` contient de l'`unsafe`. | M1 |
| `firmware/gop` | Pilote UEFI GOP (`no_std`, 7 Ko) livré dans la ROM de la carte : pilote les vrais registres SVGA et offre un framebuffer linéaire au firmware, au chargeur de Windows et à son pilote d'affichage de base. | M1 |

## Règles de sécurité

1. **Tout ce qui vient de l'invité est hostile.** `svga-core` est en `#![forbid(unsafe_code)]`.
2. **Lecture unique, puis copie, puis validation.** La configuration de la FIFO (MIN, MAX, NEXT_CMD, STOP) est figée au début de chaque passe. Chaque commande est copiée hors de la mémoire partagée avant d'être interprétée : pas de TOCTOU.
3. **Toutes les tailles sont bornées**, en arithmétique 64 bits : curseurs, escapes, commandes 3D ≤ 256 Kio. Une commande plus grande que l'anneau est rejetée, sinon on attendrait indéfiniment.
4. **Une commande incomplète n'est jamais consommée.** Une commande invalide arrête la FIFO et lève `SVGA_IRQFLAG_ERROR`, sans jamais paniquer.
5. **Budget par passe** : l'invité ne peut pas monopoliser le thread de traitement.
6. **`unsafe` confiné** à `rsvga-server` (mmap, accès volatils) et à `svga-render` (Vulkan), derrière des API sûres et documentées.
7. **Sandbox du serveur** (pas encore faite, prévue en M5) : seccomp et landlock, pour que le serveur n'accède qu'au socket vfio-user, à la mémoire invitée et à `/dev/dri/renderD*`.
8. **Fuzzing de chaque décodeur** (libFuzzer), en plus des tests unitaires et d'un test de stress déterministe.

## État de M1 (2026-11-06)

Testé avec le QEMU 11.1.2 de trixie-backports (extrait localement, sans installation), q35, KVM et OVMF :

- **Ce qui marche** : QEMU se connecte à `rsvga` et négocie la version. Il lit l'espace PCI, assigne les BAR (I/O en 0x6060, VRAM en 0x80000000, FIFO en 0x84000000) et mappe VRAM et FIFO directement dans le guest via KVM (`info mtree` : `ramd ... KVM`). Il partage la RAM du guest (fenêtres DMA avec fd).
- **Blocage 1, accès non alignés (résolu par patch)** : le protocole SVGA II lit et écrit le port de valeur en `base+1`, en 32 bits, donc non aligné. QEMU rejette ces accès sur les régions vfio, car `vfio_region_ops` (`hw/vfio/region.c`) n'a pas `.valid.unaligned`, alors que sa carte `vmware-svga` intégrée l'a. Vérifié au moniteur : les écritures d'index (alignées) arrivent, celles du port de valeur jamais. Solutions :
  1. un patch QEMU d'une ligne (`.unaligned = true` pour les régions vfio), à proposer upstream ;
  2. émuler plutôt **SVGA3** (PCI `15ad:0406`), dont les registres sont en MMIO aligné.

  Vérifié dans VMware Tools 13.1.5 (build 25544008) : l'INF du pilote Windows 10/11 x64 (`vm3d.inf`, 9.17.11.0004) ne déclare que `PCI\VEN_15AD&DEV_0405`. Seul l'ancien paquet Windows 7 (9.17.06.0005, 2023) déclare aussi `DEV_0406`. **Décision : SVGA II d'abord (avec le patch QEMU), SVGA3 ensuite comme second modèle**, utile pour Linux (`vmwgfx` gère les deux) et peut-être pour Windows avec ce vieux pilote. Le cœur reste commun aux deux modèles.

  **Résolu** par [`patches/qemu/0001-vfio-user-pass-unaligned-region-accesses-through.patch`](patches/qemu/0001-vfio-user-pass-unaligned-region-accesses-through.patch) (33 lignes). Le transport vfio-user déclare une nouvelle capacité `VFIO_IO_CAP_UNALIGNED` et ses régions acceptent les accès non alignés ; le vfio du noyau ne change pas. `scripts/build-qemu.sh` construit ce QEMU dans `target/qemu/install`. `scripts/smoke-qemu.py` le vérifie : avec le QEMU non patché, chaque lecture par le port de valeur renvoie 0 ; avec le QEMU patché, l'ID, la VRAM, le changement de mode 800×600×32 et la capture sont corrects.
- **Blocage 2, firmware (résolu)** : l'OVMF de Debian (edk2 2025.02) pilote les cartes VMware comme des cartes Bochs, via les ports VBE 0x1CE/0x1CF (`QemuVideoDxe/Driver.c` : « VMWare SVGA is handled like Bochs »), et vfio ne transmet pas ces ports. **Résolu** par notre propre pilote GOP (`firmware/gop`), empaqueté en ROM optionnelle PCI (`rsvga-server/src/rom.rs`) et servi par la région 6 de vfio-user, avec le BAR ROM dans l'espace de config. OVMF le charge depuis la carte (pilote spécifique au bus, prioritaire), et la console UEFI s'affiche sur rsvga : voir [docs/img/m1-ovmf-shell.png](docs/img/m1-ovmf-shell.png).
- **Windows** : Tiny11 (Windows 11 25H2) démarre sur rsvga (testé sur une couche qcow2 temporaire, disque d'origine intact). Le chargeur puis le pilote « Microsoft Basic Display Adapter » utilisent le framebuffer de notre GOP : le bureau s'affiche en 1280×800 au bout de 2 minutes, sans pilote VMware.
- **Pilote VMware (M1 atteint)** : le pilote officiel `vm3d` 9.17.11 (VMware Tools 13.1.5), installé par `pnputil`, se charge sur rsvga. Il négocie l'ID, démarre la FIFO, initialise les GMR par `GMR_DESCRIPTOR`, puis affiche le bureau en 1024×768 avec seulement `UPDATE` et `FENCE` (chemin framebuffer). Il **exige les interruptions** : sans elles, il tourne indéfiniment en `SYNC`/`BUSY`, car il attend la fence dans son gestionnaire d'interruption. rsvga fournit donc l'INTx de vfio-user, avec la sémantique de vfio-pci : eventfd de déclenchement, masquage automatique, démasquage par l'eventfd de rééchantillonnage de KVM, statut et acquittement par le port 8. Mesuré : 2 131 commandes, 319 fences, 319 interruptions acquittées, extinction ACPI propre en 3 s.
- **Prêts mais pas encore annoncés au pilote** : la RAM du guest (fenêtres DMA mappées et scellées), les GMR2 et les Screen Objects avec leurs blits (`twod.rs`). Ils serviront dès qu'on annoncera `SVGA_CAP_GMR2` et `SCREEN_OBJECT_2` (M2).
- **Interaction** : la fenêtre de rsvga (winit + softbuffer) envoie clavier (par position physique) et souris (tablette absolue) à QEMU par QMP. Validé en usage réel, curseur matériel de Windows compris.

## État de M2 (atteint le 2026-11-07)

- **Screen Objects (fait, vérifié sur Windows)** : rsvga annonce `SVGA_CAP_GMR2` et `SCREEN_OBJECT_2`. Le pilote `vm3d` passe alors en mode Screen Object : il décrit sa mémoire par `DEFINE_GMR2` / `REMAP_GMR2`, crée l'écran par `DEFINE_SCREEN`, puis pousse les pixels par `DEFINE_GMRFB` + `BLIT_GMRFB_TO_SCREEN`. Résultat : bureau Windows 11 en 1920×1080, sans erreur, environ 3 % d'un cœur au repos. Un écran redéfini garde ses pixels, et la fenêtre ne recopie que les lignes modifiées. Le pilote fournit aussi une zone de sauvegarde en VRAM pour chaque écran ; rsvga l'accepte sans s'en servir, car ses pixels sont en mémoire hôte.
- **Command buffers (faits, utilisés par Windows)** : `SVGA_CAP_COMMAND_BUFFERS` et `CMD_BUFFERS_2`. L'en-tête `SVGACBHeader` est lu en RAM invitée. Il y a deux contextes et le contexte « device » (start/stop, preempt, vider la file). Un contexte arrêté met les buffers en file. Une erreur arrête le contexte, ce qu'attend vmwgfx, qui le relance ensuite. Le statut et `errorOffset` sont réécrits, puis l'IRQ `COMMAND_BUFFER` est levée. L'exécution est synchrone, pendant l'écriture de `COMMAND_LOW` : les commandes du contexte « device » doivent être finies au retour. En mode guest-backed, le pilote envoie presque tout par ce canal.
- **Le pilote Windows demande d'abord à l'hyperviseur** : avant d'initialiser la carte, il appelle **`BDOOR_CMD_GET_SVGA_CAPABILITIES`** (commande 75 du port VMware, mode noyau seulement). Le type de capacité est dans le mot haut de `ECX` (`SVGABackdoorCapType` dans `svga_reg.h` : 0 = capacités de la carte, 1 = capacités FIFO, 2 = version matérielle 3D, 3 = `CAP2`...). En cas de succès, `EBX` = magic et `EAX` = valeur. Sinon `EAX` = -1 et `EBX` reste inchangé. Il n'appelle que le type 0. Le QEMU officiel répond « non géré », et le pilote se limite alors à la 2D, quoi que la carte annonce.
- **Patch QEMU 0002** ([patches/qemu/0002-vmport-answer-SVGA-capability-queries-and-GuestRPC.patch](patches/qemu/0002-vmport-answer-SVGA-capability-queries-and-GuestRPC.patch)) : deux ajouts au port VMware, désactivés par défaut. (1) `svga-backdoor` + `svga-caps`, `svga-fifo-caps`, `svga-3d-hwversion`, `svga-caps2` : la réponse à la commande 75. Les valeurs viennent de rsvga (`rsvga --vmport-args`, que `run-windows.sh` passe à QEMU) : elles sont donc toujours celles de la carte. (2) `guestrpc` : un canal GuestRPC « RPCI » minimal (cookies, envoi et réception 4 octets par 4 comme open-vm-tools). Il trace les messages, répond « OK » à `log` et « commande inconnue » à ce qu'il ne connaît pas. `info-get` et `info-set` passent par une petite mémoire de clés, l'équivalent des lignes `guestinfo.*` d'un `.vmx` : la propriété `guestinfo` (option `--guestinfo` de `run-windows.sh`) donne les valeurs de départ, et une clé absente reçoit « 0 No value found », comme sous VMware.
- **Le pilote se raconte** : par GuestRPC, `vm3d` journalise chaque décision et lit ses réglages (`info-get guestinfo.svga.wddm.*`, `guestinfo.loglevel.vm3d.*`). Avec `--trace`, tout arrive dans `target/vm/qemu.log` (trace `vmport_guestrpc_message`). C'est ce journal qui a guidé la suite : « 3D is off », « Guest backed surface is off », « requested 3D, but device does not meet minimum capability requirements (SM2) »...
- **Ce que vérifie le pilote** (établi avec `RSVGA_PROBE_CAPS`, `RSVGA_PROBE_CAPS2`, `RSVGA_PROBE_HW3D` : annonces sans implémentation, pour le diagnostic seulement) :
  - **La 3D** dépend de `SVGA_CAP_3D`, de la version matérielle 3D dans la FIFO et du **bloc de capacités 3D de la FIFO** (`SVGA_FIFO_3D_CAPS`, enregistrements `{longueur, type 0x100}` puis paires `(index, valeur)`) : le pilote ne lit pas `DEV_CAP` pour décider. Avec `SVGA3D_DEVCAP_3D = 1`, il passe « 3D is on » ; il exige aussi au moins le shader model 2 (« minimum capability requirements (SM2) »).
  - **Les objets guest-backed** demandent `SVGA_CAP_GBOBJECTS`, `CMD_BUFFERS_2` et le registre `CAP2` (et la réponse « No value found » de GuestRPC). Il lit alors les 262 `DEV_CAP`, `GBOBJECT_MEM_SIZE_KB`, `MOB_MAX_SIZE`, `SCREENTARGET_MAX_*`.
  - Avec la 3D annoncée sans la fournir, l'écran reste noir : on n'annoncera la 3D qu'avec un vrai rendu (M3, voir plus bas).
- **Objets guest-backed (fait, vérifié sur Windows)** : rsvga annonce `SVGA_CAP_GBOBJECTS`, `CMD_BUFFERS_2`, `CAP2_REGISTER` et `CAP2` = `GROW_OTABLE | GB_MEMSIZE_2 | OTABLE_PTDEPTH_2`, sans 3D. Le pilote se charge en « Display Only driver » avec « Guest backed surface is on », et affiche le bureau par **Screen Targets** : `SET_OTABLE_BASE64`, `DEFINE_GB_MOB64`, `ENABLE_GART`, `DEFINE_GB_SURFACE_V4`, `BIND_GB_SURFACE_WITH_PITCH`, `DEFINE/BIND_GB_SCREENTARGET`, puis `UPDATE_GB_IMAGE` + `UPDATE_GB_SCREENTARGET` à chaque changement, tout par command buffers. Bureau Windows 11 en 1920×1080, Explorateur et déplacements de fenêtres corrects, aucune commande en erreur ni inconnue.
  - `svga-core` : `gb.rs` décode les commandes, `layout.rs` calcule la disposition d'une surface comme vmwgfx (couches, puis niveaux de mip, en blocs du format), `mob.rs` lit les tables de pages des MOB (profondeur 0 à 2, entrées 32 ou 64 bits). La table des 153 formats (`svga-proto/src/format.rs`) est générée depuis `svga3d_surfacedefs.h` par `scripts/gen-surface-formats.py`.
  - `rsvga-server/src/gb.rs` : la liste des pages d'un MOB est lue une fois, à sa définition. Chaque surface a une copie « device » de même disposition que sa copie invitée, créée au premier besoin ; `UPDATE` copie MOB → device, `READBACK` device → MOB, `SURFACE_COPY` copie entre copies device. Un pas de ligne propre au MOB (`WITH_PITCH`) est respecté. `UPDATE_GB_SCREENTARGET` recopie la zone vers les pixels de l'écran affiché, et la fenêtre n'en reprend que la partie modifiée. Les tables d'objets sont seulement mémorisées : rsvga garde l'état de ses objets chez lui.
  - Limites : 2 Gio de MOB annoncés à l'invité (8 Gio acceptés : l'invité dépasse un peu son budget), 256 Mio par MOB, 1 Gio de copies device, 16 Screen Targets.
- **Redimensionnement depuis l'hôte (fait)** : comme sous VMware, il passe par les VMware Tools de l'invité. L'hôte leur envoie `Resolution_Set <largeur> <hauteur>` sur le canal GuestRPC « TCLO » (hôte → invité). Le patch 0002 gère ce canal : il accueille chaque canal par `reset` puis `Capabilities_Register` (les Tools n'annoncent leurs capacités que sur demande) et livre une commande en attente à chaque interrogation. Il ajoute aussi la commande QMP `x-vmport-guestrpc-send`. La fenêtre de rsvga envoie la taille choisie 300 ms après le dernier redimensionnement, bornée entre 800×600 et le maximum de la carte ; quand Windows adopte la taille, la fenêtre y est déjà et rien ne repart. Vérifié : `Resolution_Set 1600 900` envoyé par QMP fait passer Windows en 1600×900 en 2 s environ ; puis, fenêtre redimensionnée à la main, rsvga envoie `Resolution_Set 1738 1002` et `1834 1066`, et Windows redéfinit son Screen Target exactement à ces tailles. **M2 est atteint.**
- **Installer les VMware Tools** (dans l'invité, en plus du pilote) demande deux choses : (1) sur l'hôte, `options kvm enable_vmware_backdoor=Y` (`/etc/modprobe.d/`, puis recharger `kvm` toutes VM arrêtées), sans quoi les programmes en mode utilisateur n'atteignent pas le port VMware ; (2) la signature d'hyperviseur de VMware dans le CPUID, que `run-windows.sh` met par défaut (`-cpu host,kvm=off,hv-relaxed,hv-vendor-id=VMwareVMware`, `--kvm-cpu` pour revenir à KVM) : sinon l'action `VM_CheckRequirements` de l'installeur annule tout (code 1602). Installation silencieuse : `setup.exe /S /v "/qn REBOOT=R"`, puis un redémarrage (pilote souris VMware). Les Tools s'annoncent alors : `tools.capability.resolution_set 1`, `display_topology_set 2`, `resolution_server toolbox 1`...
- **Fast Startup** : un Windows arrêté normalement se met en veille prolongée. Au démarrage suivant, son pilote reprend avec les choix faits face à l'ancienne carte, sans relire les capacités. `run-windows.sh` cache donc S3 et S4 à l'invité (`-global ICH9-LPC.disable_s3=1 -global ICH9-LPC.disable_s4=1`) : chaque démarrage est complet.
- **Outils de test** : `run-windows.sh` ouvre un moniteur QEMU (HMP) sur `$XDG_RUNTIME_DIR/rsvga-vm-hmp.sock`. On peut y lire la position du curseur dans la FIFO (`xp` sur le BAR 2), déplacer la souris PS/2, envoyer des touches ou activer des traces.

## M3 : la 3D (atteint le 2026-11-07)

### Ce qui est établi (2026-11-07)

Au début de M3, la 3D restait derrière les variables de sonde (`RSVGA_PROBE_CAPS=9dc6c222 RSVGA_PROBE_CAPS2=2d RSVGA_PROBE_HW3D=20001`) tant que rsvga n'exécutait pas les commandes DX ; elle est annoncée par défaut depuis le point 12 du plan. Avec elles, **DWM tourne sur notre carte en DirectX 10.1** : il définit un contexte DX et envoie des milliers de commandes (shaders, états, vues, `DX_DRAW_INDEXED`...). L'écran reste noir, puisqu'elles ne sont pas encore exécutées. Le chemin pour y arriver :

- **Pourquoi DWM échouait** : le pilote DirectX en mode utilisateur (`vm3dum64_10.dll`) contient, pour chaque feature level (11_1, 11_0, 10_1, 10_0) et chaque version de DDI, la **valeur minimale de chaque devcap** qu'il utilise. Si aucun niveau n'est satisfait, il n'en annonce aucun : `D3D11CreateDevice` échoue avec `DXGI_ERROR_UNSUPPORTED` à tous les niveaux, DWM se rabat sur WARP, que Windows refuse sur un adaptateur 3D, et plante en boucle (`dwmcore.dll`, code `0x889800B0`, visible dans le journal Application). Points notables de ces exigences : pour les formats, `SHADER_SAMPLE` veut dire « lisible par un shader » (les formats entiers et le stencil l'ont aussi) ; `R32G32B32_*` doivent accepter les textures 3D ; `B8G8R8X8_UNORM` et `R11G11B10_FLOAT` doivent servir de format de sommets ; `MAX_TEXTURE_REPEAT` (devcap 22) est exigé ; l'interface DirectX 11.1 demande en plus `YUY2` et `NV12`. La table de rsvga (`devcaps.rs`) suit maintenant ce que rapporte un vrai GPU Direct3D 11, et un test vérifie qu'elle couvre toutes les exigences du niveau 10_1.
- **Ce que le pilote noyau vérifie** : sa version *debug* (livrée avec les Tools, choisie par `guestinfo.svga.wddm.buildType=debug`) refuse par assertion les combinaisons impossibles (formats typeless ou de profondeur comme cible couleur, `R9G9B9E5` rendable...). Il refuse aussi de créer une surface dont le format n'est pas « supporté » : DWM utilise `ALPHA8` (le nom Direct3D 9 de `A8_UNORM`) pour son atlas de glyphes, et le pilote utilise `A8R8G8B8` pour `B8G8R8A8_UNORM` ; ces anciens noms ont donc les capacités de leur équivalent DXGI.
- **`DX_PRESENTBLT`** est implémenté (copie, mise à l'échelle au plus proche, inversion rouge/bleu RGBA↔BGRA, affichage immédiat si un Screen Target montre la destination) : c'est ainsi que le pilote présente, DirectX ou pas.
- **Niveau obtenu** : feature level 10_1 (SM 4.1). Annoncer le SM5 (devcap 258, `CAP2_DX3`) ouvre le 11_0 côté noyau ; il faudra alors aussi les shaders de calcul, de tessellation et les UAV (M4).
- **Direct3D 9** passe par un autre chemin (contextes 3D anciens) : voir les points 9 et 10 du plan.

### Outils de diagnostic

- `guest/d3dtest/d3dtest.c` : vérifications de rendu Direct3D 11, pixel par pixel (triangle et interpolation, tampons de constantes et quad indexé, texture, profondeur 24 et 32 bits, mélange, instanciation, cible entière, ciseaux, `SV_VertexID`, résolution 4×, `GenerateMips`), puis une fenêtre avec swap chain laissée quelques secondes à l'écran. Shaders HLSL compilés dans l'invité par `d3dcompiler_47.dll`. Le test lui-même est validé sous Wine sur l'hôte (13/13).
- `guest/d3d9test/d3d9test.c` : vérifications de rendu Direct3D 9, pixel par pixel : effacements (entier, rectangle, limité au viewport), sommets pré-transformés (couleurs interpolées, centres de pixels sur les entiers), transformations et éclairage du pipeline fixe, étages de texture (`MODULATE`, `ADD`), shader models 2 et 3 (constantes, déclaration de sommets, indices avec sommet de base, boucle sur une constante entière, texture), profondeur, mélange, test alpha, brouillard, ciseaux, viewport, `StretchRect` et `ColorFill`, requêtes d'événement et d'occultation, puis une fenêtre avec sa swap chain. `ninetest.cmd` le lance (`guest-run.sh ninetest`). Validé d'abord sous le rendu logiciel de Windows et sous Wine sur l'hôte ; s'y sont ajoutés sRGB, sprites, plans de découpe, textures cube et volume, mipmaps générés, cibles multiples, stencil double face, brouillard par sommet, instanciation, texture de sommets, shaders 1.x (assemblés à la main), sous-programme, décalages de départ, carte d'ombres et `INTZ`.
- `guest/umdcaps` : charge le pilote D3D9 en mode utilisateur que le noyau désigne, appelle son `OpenAdapter` (ses requêtes vont au noyau par `D3DKMTQueryAdapterInfo`) puis `GetCaps` comme le runtime, et rapporte le code d'erreur, les données privées que lui passe le pilote noyau (drapeaux, puis le tableau des devcaps à partir de l'octet 0x68), sa liste de formats et ses `D3DCAPS9`.
- `guest/d3d9trace` : ce que le runtime D3D9 demande au pilote (appels du pilote en mode utilisateur et de l'interface noyau `D3DKMT*`, avec leurs résultats), et `retrace` la même chose avec la liste des modes réécrite. `guest-run.sh --admin` lance un outil en administrateur (Ctrl+Maj+Entrée puis Alt+Y sur l’invite UAC de ce Windows en anglais) ; `dxg` active les canaux d'événements détaillés du noyau graphique, `events` les lit.

### Plan

1. **Décodage des commandes DX** (fait) : `svga-core/src/dx.rs` décode 90 commandes DX : celles de DirectX 10/10.1 (contextes, tables d'objets, états, vues, shaders, liaisons, dessins, copies, requêtes, fences, transferts), plus les variantes `_V2`, `GROW_COTABLE` et les copies de résolution et de conversion. Chaque champ est typé, chaque tableau borné par les limites de Direct3D (8 cibles, 32 tampons de sommets, 128 vues...), les énumérations fermées vérifiées ; tests et cible de fuzzing (`fuzz/run.sh dx`). Le serveur décode et trace (`DX <contexte> <commande>`) sans exécuter encore. Vérifié avec DWM : 26 701 commandes en une minute de bureau, sur 6 contextes, aucune refusée ni inconnue. Les commandes du shader model 5 (UAV, calcul, dessins indirects) viendront avec M4.
2. **État des contextes DX** (fait) : `svga-core/src/cotable.rs` donne le format exact de chaque entrée de table d'objets (tailles vérifiées en compilant les en-têtes VMware) : encodage et décodage, l'entrée passant par l'analyseur de sa commande `DEFINE`. `rsvga-server/src/dxctx.rs` garde les contextes (au plus 256), leurs douze tables liées à un MOB (un identifiant d'objet doit tenir dans la table : la taille du MOB borne la mémoire), les objets, l'état du pipeline (shaders, vues, tampons, états, fenêtres de rendu, ciseaux, stream output, prédication) et le code des shaders, copié hors du MOB au `BIND_SHADER` (64 Mio en tout, 4 Mio par shader). Le pilote Windows agrandit ses tables par `DX_GROW_COTABLE` : les objets suivent. `DX_SET_COTABLE` avec contenu valide recharge une table depuis son MOB, `DX_READBACK_COTABLE` l'y écrit. Les fences 64 bits et les transferts MOB ↔ surface sont exécutés ; les requêtes se terminent tout de suite avec des résultats « visible, rien de compté » en attendant le GPU. Sauvegarder ou restaurer l'état complet d'un contexte (`READBACK_CONTEXT`, `BIND_CONTEXT` avec contenu valide) n'est pas fait : Windows ne s'en sert pas. Vérifié avec DWM : 28 265 commandes, 25 176 exécutées, 3 089 en attente du rendu (dessins, copies, effacements), aucune refusée.
3. **`svga-render`** (Vulkan via `ash` 0.38, sur la RX 6950 XT) — **fondations faites** : le GPU est le plus gros GPU dédié (ou celui que nomme `RSVGA_GPU`, par exemple `llvmpipe`). Une surface devient une `VkImage` ou un `VkBuffer` dont les octets ont la disposition de sa copie invitée : les formats ne correspondent qu'à des formats Vulkan de même disposition, et l'envoi comme la relecture passent sans conversion par des tampons intermédiaires. Toutes les images restent en layout `GENERAL`, les opérations sont séparées par des barrières complètes, le travail est soumis à la fin de chaque command buffer de l'invité : simple et correct, à affiner avec les dessins. `rsvga-server/src/gpu.rs` garde chaque surface cohérente : il retient quel côté (copie hôte ou GPU) a été écrit en dernier et copie avant que l'autre ne serve (relecture vers l'invité, affichage, copie CPU, envoi depuis le MOB). Exécutés sur le GPU : `CLEAR_RENDERTARGET_VIEW`, `PRED_COPY(_REGION)`, `BUFFER_COPY`, `TRANSFER_FROM_BUFFER`, `SURFACE_COPY_AND_READBACK`. **Premier rendu vérifié** : sous Windows, `d3dprobe` efface une cible en rouge, la copie et relit `0xffff0000`, le tout exécuté par la RX 6950 XT. Les formats de profondeur 24 bits (stockés en 32 bits flottants sur AMD) et les surfaces multi-échantillonnées ne font pas encore l'aller-retour : ils vivent sur le GPU seulement, sans envoi ni relecture.
4. **Traducteur de shaders VGPU10 → SPIR-V** (fait pour les vertex et pixel shaders SM4.0/4.1) : crate `svga-shader`, en Rust sûr. Le décodeur lit le flux de jetons (instructions, opérandes avec index relatifs, modificateurs, jetons étendus, déclarations) en bornant tout. Le traducteur représente chaque registre SM4 par un `vec4` flottant et réinterprète les bits pour les opérations entières. Il copie entrées et sorties à l'entrée et au retour, et fait du contrôle de flux (`if`, `loop`, `break(c)`, `ret(c)`, `discard`) des constructions structurées SPIR-V. Il couvre l'arithmétique flottante et entière, les comparaisons, conversions, dérivées, `sample`/`_l`/`_b`/`_d`, `ld`, `resinfo`, le tampon de constantes immédiat, les valeurs système (position, `VertexID`/`InstanceID` sans la base, face, primitive, échantillon) et l'interpolation. Liaisons : ensemble 0, 256 numéros par étage (constantes à partir de 0, échantillonneurs de 16, ressources de 32). Au `BIND_SHADER`, rsvga traduit tout de suite et journalise un refus avec sa raison. Vérifié : les 37 shaders de DWM capturés (`RSVGA_SHADER_DUMP`, gardés hors du dépôt car c'est du code Microsoft) passent `spirv-val` (règles Vulkan 1.3), et sous Windows les 86 liaisons de shaders de DWM sont toutes traduites. Une cible de fuzzing (`fuzz/run.sh shader`) a trouvé puis fait corriger un accès non vérifié. Restent `switch`, les geometry shaders, les `sample_c` (comparaison), l'échantillonnage multi-échantillons, puis le SM5.
5. **Pipelines et dessins** (fait) : `svga-render/src/draw.rs` fait de l'état Direct3D 10 un pipeline Vulkan, en rendu dynamique (`VK_KHR_dynamic_rendering`, cœur 1.3) avec des descripteurs poussés (`VK_KHR_push_descriptor`). Tout est mis en cache : modules SPIR-V, dispositions de descripteurs, pipelines (clé : tout l'état fixe), vues d'images et de tampons (avec leur surface), échantillonneurs. Fenêtre de rendu, ciseaux, facteur de mélange, référence de stencil et pas des sommets restent dynamiques. L'axe y de Direct3D est rendu par une fenêtre de rendu de hauteur négative (le sens des faces suit sans autre calcul). Un emplacement vide lit des zéros, comme sous Direct3D : tampon, images 1×1 et vue de tampon nulles. Les vues de profondeur lisibles (`R32_TYPELESS` liée en profondeur) deviennent de vraies images de profondeur, lues par leur aspect profondeur. Côté périphérique, `rsvga-server/src/gpu.rs` rassemble à chaque dessin l'état du contexte (shaders, disposition des sommets, tampons, vues, états ou leurs valeurs par défaut) et retraduit un shader quand des sommets ou des cibles sont entiers (les types SPIR-V doivent correspondre ; traductions en cache). Les fonctions facultatives (anisotropie, `MIRROR_ONCE`, profondeur non découpée, `A8_UNORM`) sont prises si le GPU les a : llvmpipe dessine aussi. Tests sur le GPU : triangle à l'endroit avec ses constantes (et éliminé vu de dos), quad indexé texturé devant puis derrière une profondeur, lecture d'une vue de tampon, et un triangle dessiné par un contexte DX jusqu'à la relecture par l'invité. **Vérifié avec Windows** : DWM compose le bureau, le menu Démarrer et l'Explorateur par la RX 6950 XT (3 401 dessins en quelques minutes, aucun refusé), texte et icônes nets. Pas encore dessinés : geometry/hull/domain shaders, stream output, vues de tampons brutes ou structurées, cibles 3D ; la prédication est ignorée.
6. **Présentation** : les Screen Targets sont alimentés depuis le GPU par une copie sans attente de la zone affichée (fait, point 11). Plus tard : dmabuf, sans copie vers le processeur.
7. **Critères** : le bureau de DWM s'affiche correctement en 3D (atteint) ; `d3dprobe` relit du rouge (atteint) ; `d3dtest` (triangle D3D11 et 12 autres vérifications) passe en entier (atteint, 13/13) ; `dxdiag` sans erreur (atteint : « No problems found », DirectDraw, Direct3D et AGP activés). Pour y arriver : résolution multi-échantillons (`DX_RESOLVE_COPY`), copies avec mise à l'échelle et conversion (`DX_PRED_CONVERT(_REGION)`) et génération des mips (`DX_GENMIPS`) sur le GPU.
8. **Mémoire** : un invité peut remplir tout son budget graphique (chaque fenêtre console redessinée crée des textures que le pilote ne libère que sous la pression). Deux corrections : le plafond de pages de MOB de rsvga a de la marge au-delà du budget annoncé (l'invité le dépasse un peu ; un `DEFINE_MOB` refusé cassait tout ensuite), et les copies device ne restent plus pour les surfaces que le GPU tient : celle qui ne sert qu'à remplir le GPU est libérée aussitôt, les autres le sont sous pression à la fin de chaque command buffer, et reviennent du GPU quand il le faut.
9. **Avant d'annoncer la 3D par défaut** : Direct3D 9. Sans la 3D, Windows rend en logiciel (Microsoft Basic Render Driver) : D3D11 jusqu'au niveau 11_1 et D3D9 (shader model 3) marchent, lentement. Avec la 3D, la RX 6950 XT rend, mais seulement aux niveaux 10_1 et 10_0, et D3D9 échoue (`D3DERR_NOTAVAILABLE`) : annoncer la 3D par défaut casserait les programmes D3D9 qui marchent aujourd'hui en logiciel. Ce qu'on sait (novembre 2026) :
   - Le pilote D3D9 de VMware (`vm3dum64.dll`, chargé par `vm3dum64_loader.dll`) parle le protocole SVGA3D **ancien** (états de rendu, pipeline fixe, shaders D3D9), pas les contextes DX10. Il construit ses caps D3D9 à partir des devcaps anciens (indices 0 à 98), que rsvga laissait à 0. Ils décrivent maintenant un périphérique shader model 3 (`devcaps.rs`) et la liste de formats D3D9 (`SURFACEFMT_*`, bits `D3DFORMAT_OP_*`), avec le format du bureau « mode d'affichage, accéléré en 3D ». Interrogé directement (`guest/umdcaps`, qui appelle son `OpenAdapter` et `GetCaps` comme le runtime), le pilote répond un périphérique complet : VS et PS 3.0, textures 16384, 8 lumières, 33 formats, multi-échantillonnage, toutes les requêtes de caps réussies.

Le pilote noyau de VMware ne passe en WDDM 1.2, 1.3 ou 2.0 que si l'appareil annonce `SVGA_CAP2_DX3` **et** `SVGA_CAP2_VIDEO_BLT` (vrai sur tout hôte VMware récent) ; sinon il reste en WDDM 1.1 (ce que montre `dxdiag`). Avec ces deux bits et WDDM 2.0 coupé (`guestinfo.svga.wddm.enableWDDMv2_0=FALSE`), il tourne en WDDM 1.2 et D3D11 gagne les niveaux 9_1 à 9_3 et le support vidéo, mais D3D9 reste refusé. Le pilote D3D9 ne se déclare à l'interface WDDM 2.0 (`0x5002` au lieu de `0x3004`) qu'avec le pilote noyau en WDDM 2.0 ; avec les deux bits et WDDM 2.0 (le choix par défaut du pilote), le pilote noyau démarre puis se décharge, et Windows retombe sur l'affichage de base.

Le pilote D3D9 se déclare alors à l'interface WDDM 2.0 (`0x5002`). DWM compose, `d3dtest` passe 13/13, D3D11 gagne les niveaux 9_1 à 9_3, aucune commande refusée ; la file haute priorité (contexte 1) sert réellement.
   - **D3D9 est accepté** (même en WDDM 1.1, sans les bits ci-dessus). `guest/d3d9trace` détourne l'import de `GetProcAddress` de `d3d9.dll` et ses appels `D3DKMT*`, ce qui montre tout ce que le runtime demande au pilote ; ses symboles publics (`d3d9.pdb`, téléchargés depuis le serveur de symboles de Microsoft dans `target/symbols`, jamais publiés) donnent ses règles. Dans `FetchDirectDrawData`, le runtime **désactive tout le pilote** s'il annonce `D3DFORMAT_OP_3DACCELERATION` sur un format avec alpha ou sans `DISPLAYMODE`, `MEMBEROFGROUP_ARGB` hors de ses formats (R8G8B8, A8R8G8B8, X8R8G8B8, R5G6B5, X1R5G5B5, A1R5G5B5, A2R10G10B10, les formats 31 à 33 et 36, et les deux formats flottants ARGB), R5G6B5 et X1R5G5B5 tous deux en mode d'affichage, des paires de formats de profondeur inversés, ou sans `D3DDEVCAPS2_STREAMOFFSET` ; puis `CEnum::GetDeviceCaps` répond `D3DERR_NOTAVAILABLE` faute d'un format « accéléré en 3D ». Le coupable était A4R4G4B4 avec `MEMBEROFGROUP_ARGB`. Ces règles sont maintenant des tests de `devcaps.rs`. Le runtime offre alors un périphérique matériel (VS et PS 3.0) et `CreateDevice` réussit ; le pilote envoie aussitôt des commandes SVGA3D anciennes (`DEFINE_GB_CONTEXT`, `BIND_GB_CONTEXT`, `SETRENDERSTATE`, `SETTEXTURESTATE`...) : point 10.
10. **Direct3D 9 dessine** (fait pour ce que couvre `d3d9test`, 37/37 avec le pilote de VMware ; `d3dtest` reste à 13/13 ; **Unigine Heaven 4.0 tourne en Direct3D 9**). Les tampons de sommets et les textures sont des surfaces guest-backed ordinaires ; la relecture (`GetRenderTargetData`) est un `READBACK_GB_SURFACE` de la cible. **Le pilote émule lui-même le pipeline fixe** avec des vs_2_0 et ps_2_0 qu'il génère : aucun `SETTRANSFORM`, `SETMATERIAL` ni `SETLIGHTDATA`. Restent à l'appareil le test alpha, le brouillard (avant le shader model 3), l'ombrage plat, et les sommets pré-transformés (`POSITIONT`), qui sautent le vertex shader même quand le pilote en laisse un lié.
    - `svga-core/src/legacy.rs` décode ces commandes (contextes, shaders, constantes, états, cibles, dessins, requêtes, `STRETCHBLT`, `GENERATE_MIPMAPS`), tableaux bornés par les limites du protocole (32 déclarations, 32 plages) ; tests et cible de fuzzing (`nine`).
    - `rsvga-server/src/ctx9.rs` garde l'état : états de rendu et de texture (avec les défauts de Direct3D 9), cibles, viewport, plage de profondeur, ciseaux, shaders liés, et leurs constantes déjà rangées comme le bloc uniforme des shaders. Le code d'un shader est lu dans son MOB au `BIND_GB_SHADER`.
    - `svga-shader/src/d3d9.rs` traduit le bytecode Direct3D 9 (vs_1_1 à vs_3_0, ps_1_1 à ps_3_0) : chaque registre est un `vec4` en variable de fonction, `a0`/`aL`/`i#` sont entiers, `b#`/`p0` booléens ; arithmétique, matrices, `lit`, `sincos`, `texld` et ses variantes, `texkill`, dérivées, prédication, `if`/`loop`/`rep`/`break` en flux structuré. Constantes, entiers, booléens et paramètres de l'appareil vivent dans un bloc uniforme par étage ; les `def` du programme y remplacent les valeurs (adressage relatif compris). Entrées et sorties sont liées par sémantique (une location par sémantique). L'appareil y ajoute test alpha, brouillard, ombrage plat ; il fournit son propre vertex shader pour les sommets pré-transformés (coordonnées d'écran ramenées en coordonnées de découpe par le viewport). Les instructions d'adressage de texture des ps_1_x (`texbem(l)`, `texreg2*`, `texm3x2*`, `texm3x3*` avec reflets, `texdp3*`, `texdepth`, `bem`) lisent la matrice de bosselage de leur étage dans le bloc uniforme. Les sous-programmes (`call`, `callnz`) sont copiés en ligne, la récursion refusée. Refusés pour l'instant : un `ret` à l'intérieur d'un `if` ou d'une boucle, les échantillonneurs de comparaison. Testé avec `spirv-val` sur des programmes écrits à la main et sur tous ceux capturés dans l'invité (`RSVGA_SHADER_DUMP`, gardés hors du dépôt), plus des programmes abîmés au hasard.
    - `rsvga-server/src/gpu/nine.rs` dessine : sommets liés à leurs déclarations par sémantique (types entiers convertis), états de rendu traduits en états Direct3D 10 pour le moteur, états de texture en échantillonneurs, constantes passées avec le dessin (nouveau `Resource::Data` de `svga-render`). Direct3D 9 place les centres de pixels sur les entiers : la fenêtre de rendu est décalée d'un demi-pixel. Effacements par rectangles (`clear_rects`), requêtes d'occultation qui comptent vraiment les échantillons (un pool de requêtes Vulkan). Test sur le GPU : un quad texturé de sommets pré-transformés, compté par une requête, jusqu'à la relecture par l'invité.
    - **Ce que la seconde série de vérifications a appris** (sRGB, points, plans de découpe, textures cube et volume, mipmaps générés, cibles multiples, stencil double face, brouillard par sommet, instanciation, texture lue par le vertex shader, ps_1_1 et ps_1_4, `texbem`, `texm3x2tex`, sous-programme, décalages de départ) : le pilote dit « sRGB » par des gammas, 2,2 dans l'état de texture `GAMMA` pour la lecture et dans l'état de rendu `OUTPUTGAMMA` pour l'écriture (rsvga prend alors les vues `_SRGB` : le mélange reste linéaire). Un point reçoit sa taille de l'état `POINTSIZE`, bornée par `POINTSIZEMIN`/`MAX`, que le vertex shader écrit si le programme ne le fait pas ; un sprite remplace les coordonnées de texture du pixel shader par `PointCoord`. Les plans de découpe arrivent déjà en espace de découpe et deviennent des `ClipDistance`. Une texture `AUTOGENMIPMAP` est déclarée avec **un seul** niveau et le drapeau `SVGA3D_SURFACE_AUTOGENMIPMAPS` : l'appareil garde sur le GPU la chaîne complète derrière ce niveau et la remplit à `GENERATE_MIPMAPS`. Instanciation, textures de sommets (étages 16 à 19), cubes, volumes, cibles multiples et stencil double face marchaient sans rien de plus.

Heaven trouve alors tout ce qu'il cherche (ombres matérielles ATI et NVIDIA, fetch 4, texture de sommets, HDR, compression ATI) et rend ses scènes justes (dirigeable, ombres des cordages, profondeur de champ, dragon), sans aucune commande refusée : 443 810 dessins en deux minutes. 4 images par seconde avec la trace, 10 à 12 sans au départ (`RSVGA_TRACE=0`), **25 à 30 aujourd'hui en WDDM 2.0** (16 à 18 en WDDM 1.1) : voir le point 11.

11. **Performances** (Heaven en Direct3D 9, 1280×720, WDDM 2.0 : de 10–12 à 35–38 images par seconde ; WDDM 1.1 : de 10–12 à 16–18). `RSVGA_PROFILE=1` (`rsvga-server/src/prof.rs`) journalise toutes les cinq secondes le temps passé par catégorie (command buffers, commandes GB, DX, D3D9, traductions, enregistrement des dessins, attente du GPU, envois, relectures, et le temps de travail du GPU lui-même, `gpu busy`, mesuré par des horodatages Vulkan au début et à la fin de chaque soumission) et, par type de commande, ce qui a forcé une relecture ; `RSVGA_TRACE=0` garde le serveur silencieux pendant une mesure. Ce qui a compté, dans l'ordre :
    - **Command buffers asynchrones.** QEMU attend la réponse à chaque écriture vfio-user de cet appareil (il a des zones projetées, qui interdisent les écritures « postées ») : le vCPU qui écrivait `SVGA_REG_COMMAND_LOW` restait immobile pendant que rsvga exécutait tout le buffer, GPU compris. Un fil de travail (`rsvga-cb`) les exécute maintenant dans l'ordre de soumission, en prenant le verrou commande par commande ; l'invité apprend la fin par l'état du buffer et l'interruption. Les buffers du contexte de contrôle et la FIFO attendent que la file soit vide (`Svga::drain`) : en WDDM 2.0, Windows préempte le contexte 0 en permanence, et des buffers rendus « préemptés » étaient resoumis dans le désordre (surfaces inconnues, puis plantage de l'invité). `RSVGA_SYNC_BUFFERS=1` rétablit l'exécution synchrone.
    - **Un rendu dynamique pour plusieurs dessins.** Chaque dessin ouvrait et fermait le sien, après une barrière complète : des dessins successifs aux mêmes cibles, qui ne lisent pas ces cibles et ne comptent pas d'occultation, continuent maintenant le même (`draw::Pass`). L'attente du GPU par buffer est passée de 1,5 s à 0,3 s par tranche de 5 s.
    - **Moins de travail par dessin** (de 19 à environ 6 µs de CPU) : le hachage FNV du SPIR-V entier, refait quatre fois par dessin pour retrouver modules et pipelines, est calculé une fois à la traduction (`Shader::hash`) ; les traductions D3D9 sont retrouvées par l'adresse de leur code (qui reste la même quand le pilote relie le même shader) ; les constantes sont découpées dans des blocs de 4 Mio recyclés au lieu de deux allocations Vulkan par dessin (le pilote en limite le nombre) ; le format d'une surface se lit sans copier sa disposition ; un dessin est construit une fois par commande.
    - **`DX_PRESENTBLT` et `SURFACE_COPY` sur le GPU** quand la source y est : la présentation de chaque image ne relit plus le tampon arrière pour le recopier sur le processeur.
    - **Soumissions sans attente** : quatre soumissions peuvent être en vol (`Frame` : command buffer, fence, tampons temporaires et blocs de constantes libérés quand elle se termine). Le GPU ne lit jamais la mémoire de l'invité directement, seulement des copies de rsvga : un buffer peut donc se terminer avant le GPU ; seules les relectures attendent. Les résultats d'occultation sont écrits à la fin du buffer, ou quand l'invité attend la requête.
    - **L'écran relu sans attendre** (`rsvga-server/src/gpu/screen.rs`). La fenêtre de rsvga montre des pixels gardés par l'appareil ; quand l'image d'un screen target vient du GPU, `BindScreenTarget` et `UpdateScreenTarget` lancent une copie de la zone vers la mémoire de l'hôte (`Renderer::read_async`) au lieu de relire toute la surface en attendant le GPU. Les pixels arrivent à l'écran quand le GPU a fini : c'est vérifié après chaque buffer et avant chaque rafraîchissement de la fenêtre. Les lectures arrivent dans l'ordre ; une lecture qu'une suivante recouvre est sautée ; un affichage depuis la copie de l'appareil attend d'abord les lectures en cours, pour qu'une image plus ancienne ne remplace jamais une plus récente. `SURFACE_COPY` et `DX_PRESENTBLT` vers la surface affichée restent donc sur le GPU : la copie de l'écran de DWM (1834×1066, à chaque image en WDDM 2.0) ne repasse plus par le processeur.
    - **Des soumissions par lots de 512 dessins.** Le GPU ne démarrait qu'à la fin de chaque buffer, et un buffer de Heaven compte jusqu'à 3 800 commandes : la relecture que le pilote demande à chaque image attendait tout ce travail. Le GPU travaille maintenant pendant l'enregistrement de la suite, et cette relecture est passée de 9,7 à 4,6 ms.
    - **Les petits envois dans les blocs recyclés.** Chaque envoi (environ 25 par image : tampons de sommets, constantes) allouait sa propre mémoire Vulkan ; ceux de moins de 4 Mio prennent leur place dans les blocs des constantes, recyclés d'une soumission à l'autre (au multiple de la taille d'un texel). Le temps des envois a été divisé par trois, et le temps noyau du fil de travail est passé de 18 % à 4 %.
    - **Ce qui reste.** Le GPU ne travaille que 25 à 30 % du temps : ce sont les attentes qui limitent. Il reste une relecture par image, demandée par le pilote : après le `DX_PRESENTBLT` de la fenêtre Direct3D 9, un `READBACK_GB_SURFACE` de la surface de destination (1280×720), que l'invité attend. La rendre asynchrone demanderait de retarder tout ce que l'invité peut observer après elle : la fin des buffers, les `MOB_FENCE`, les autres relectures, et toute lecture du même MOB. En WDDM 1.1, Heaven reste à 16–18 images par seconde alors que l'appareil n'est occupé que 34 % du temps et le GPU 13 % : quelque chose côté invité donne le rythme, ce qui reste à comprendre. L'affichage par dmabuf (point 6) supprimerait aussi la copie de l'écran vers le processeur.

12. **La 3D par défaut** (fait). Sans aucune variable, l'appareil annonce la 3D en WDDM 2.0 : `CAPABILITIES_3D` (`THREE_D`, `DX`, `HP_CMD_QUEUE`), `CAPABILITIES_2_3D` (`DX2`, `DX3`, `VIDEO_BLT`) et la version matérielle 3D `0x20001`, exactement la sonde de tous les essais (`rsvga-server/src/device.rs`). `RSVGA_3D=0`, ou `run-windows.sh --no-3d`, garde la 2D : le pilote passe en affichage seul et Windows rend la 3D en logiciel. Sans GPU Vulkan, rsvga reste en 2D tout seul. En vérifiant ce cas, un plantage est apparu : quand aucun GPU ne convenait, le chargeur Vulkan était libéré avant la destruction de l'instance ; c'est corrigé et testé. Les variables `RSVGA_PROBE_*` gardent le dernier mot, pour le diagnostic.
    - **Vérifié dans la VM de test** :
      - dxdiag : WDDM 2.0, niveaux 10_1 à 9_1, DDI 11.3 ;
      - d3dtest, avec un nouveau test du processeur vidéo, et d3d9test 37/37 ;
      - des changements de résolution (`guest/modes` : 1280×720, 1024×768, retour) ;
      - Heaven ;
      - un redémarrage de Windows (`guest/reboot.cmd`), puis d3dtest ;
      - un démarrage en 2D, où d3dtest passe sur WARP au niveau 11_0.
    - **La vidéo.** `VIDEO_BLT`, sans lequel le pilote ne passe pas en WDDM 2.0, n'était annoncé que de nom : les blits du processeur vidéo de Direct3D 11 restaient noirs. Pour chaque `VideoProcessorBlt`, le pilote envoie une commande absente des en-têtes publics, 1295 (`VIDEO_BLT` ici). `guest/videoprobe` fait une série de blits en variant chaque paramètre, ce qui a permis de la décoder (`svga-core/src/gb.rs`, `VideoBlt`). C'est une structure compacte de 168 octets, alignée à l'octet près :
      - la sortie : surface, mip, tranche, couleur de fond RGBA ou YCbCr, rectangle cible ;
      - un flux : surface, mip, tranche, rectangle source, rectangle de destination, rotation, format de trame.

      L'alpha du flux, les espaces de couleur et le remplissage alpha ne sont pas transmis : le pilote ne les propose pas. Son processeur annonce un seul flux, la rotation, B8G8R8A8/X8 et NV12 en entrée et en sortie, et YUY2 en entrée. `rsvga-server/src/gpu/video.rs` l'exécute : le fond, puis la copie mise à l'échelle avec filtrage linéaire sur le GPU. Les sources YUV et les rotations passent d'abord par le processeur, qui les convertit en BGRA dans une image de travail (BT.601 sous 720 lignes, BT.709 au-delà, plage limitée), copiée ensuite de la même façon. Les identifiants de surface à partir de `0xFFFFFF00` sont réservés à l'appareil pour cette image.
    - **NV12.** Le format est annoncé, parce que l'interface DirectX 11.1 l'exige, mais sa définition était refusée (`Planar`) : le pilote enchaînait les erreurs et Windows retirait le périphérique au programme. Les formats plans NV12 et YV12 ont maintenant leur disposition : le plan de luminance, puis la chrominance. Ils restent dans la copie de l'appareil, où se font aussi leurs copies DX.
    - **Pas encore** : la sortie NV12 du processeur vidéo, les vues de shader sur les plans d'une surface NV12 (R8, R8G8), le désentrelacement. Le décodage vidéo matériel n'a pas été examiné. Côté pilote de VMware, deux limites, sans aucune commande vers rsvga :
      - une texture YUY2 liée en cible de rendu le fait échouer lui-même (« erreur interne », `0x887a0020`, et Windows retire le périphérique) ;
      - il refuse une vue d'entrée du processeur vidéo sur une YUY2 liée en lecture seule.

## M4 : Direct3D 11 au niveau 11_0 (en cours, 11_0 annoncé par défaut)

1. **Ce que le pilote exige.** Le pilote DirectX de VMware (`vm3dum64_10.dll`) garde une table de minimums de devcaps par niveau (voir M3, point « Pourquoi DWM échouait »). Pour 11_0 elle ajoute aux exigences de 10_1 : des textures de 16 384 texels (`MAX_TEXTURE_WIDTH`, `HEIGHT`, `REPEAT`), les formats BC6H et BC7, `SM5` et `MULTISAMPLE_8X` (pour l'interface 11.0 et au-delà). Celle de 11_1 est la même ; Windows refuse pourtant 11_1 (`DXGI_ERROR_UNSUPPORTED`), pour une raison à trouver. rsvga annonçait déjà tout le reste : avec le seul devcap `SM5`, `dxdiag` montre les niveaux 11_0 à 9_1, et DWM tourne. Il est maintenant annoncé par défaut (`RSVGA_PROBE_DEVCAPS="258=0"` revient à 10_1).
2. **Les commandes que le pilote change** à ce niveau, même pour un programme Direct3D 10 : ses copies vers et depuis les ressources « staging » passent par `DX_PRED_STAGING_COPY_REGION` et ses sœurs (`Staging` dans `svga-core/src/dx.rs` : la copie, puis la relecture de la destination si demandée), il lie les vues UAV à chaque changement de cibles (`DX_SET_UA_VIEWS`, même vides) et donne à chaque contexte une zone de MOB pour les interfaces de classes (`DX_BIND_SHADER_IFACE`). Avec elles, `d3dtest` repasse au niveau 11_0.
3. **`d3dtest` couvre maintenant Direct3D 11** : comparaison de profondeur, gather, geometry shader, stream output, et au niveau 11_0 compute shaders (vue typée, tampons structurés et bruts, mémoire partagée, atomiques, instructions sur les bits), UAV dans un pixel shader, tessellation, dessin et dispatch indirects. Ce qu'un niveau ne permet pas est sauté (`SKIP`). Résultats dans la VM de test, au niveau 11_0 annoncé par défaut : `dxdiag` montre 11_0 à 9_1 en WDDM 2.0, les 26 tests de `d3dtest` (27 avec celui des requêtes, point 8) passent avant et après un redémarrage de Windows, `d3d9test` reste à 37/37, Heaven tourne en Direct3D 9 et en Direct3D 11, et en 2D `d3dtest` passe sur WARP. Avant, à la sonde : au niveau 10_1 (le défaut), les 14 tests d'avant plus la comparaison de profondeur, le gather et le geometry shader, et `d3d9test` reste à 37/37.
4. **Shader model 5 dans le traducteur** (`svga-shader/src/translate/`) :
   - `bits.rs` : `countbits`, `firstbit_*` (comptés depuis le bit de poids fort, ~0 sans bit, comme Direct3D), `ubfe`, `ibfe`, `bfi` avec les règles de Direct3D, `bfrev`, demi-flottants, retenues, produits complets, `swapc` ;
   - `memory.rs` : tampons bruts et structurés en tampons de stockage de mots, mémoire partagée de groupe en tableau `Workgroup`, vues typées en images de stockage de format inconnu (sauf `R32` pour les atomiques), atomiques, `sync`, `bufinfo` ;
   - `geometry.rs` : geometry shaders (entrées par sommet, `emit`, `cut`, instances, couche et viewport en sortie) ;
   - `tessellation.rs` : hull et domain shaders. Les phases d'un hull shader (points de contrôle, puis les phases « fork » et « join » des constantes de patch, chacune avec ses instances) deviennent des fonctions du tessellation control shader de Vulkan (le module SPIR-V sait maintenant en faire plusieurs ; les registres passent alors en `Private`, partagés par les phases). L'entrée appelle la phase des points de contrôle, ou les recopie quand le shader n'en a pas, attend toutes les invocations, puis la première exécute les phases de patch et écrit les niveaux de tessellation. Les constantes de patch vivent jusque-là dans un tableau de registres, que les phases indexent (`o[r0.x + 4]`). Le domain shader lit le point du domaine, les points de contrôle et les constantes de patch (les facteurs depuis les niveaux de tessellation). Les signatures que le pilote ajoute après chaque shader (`SVGA3dDXSignatureEntry`) disent quels registres recopier et lesquels sont la position ;
   - `xfb.rs` : le stream output, par l'extension Vulkan transform feedback. Le dernier stage avant le rastériseur réécrit chaque registre capturé dans une variable de ses seules composantes, décorée de son tampon, du pas du tampon et de son décalage ; ces variables prennent des emplacements que le shader n'utilise pas, en partant du haut ;
   - comparaisons de profondeur (`sample_c`, `sample_c_lz`) et gathers (`gather4`, `_c`, `_po`) ;
   - le stage compute : groupes, identifiants de threads.
   Les 103 shaders capturés (DWM et `d3dtest`, gardés hors du dépôt) se traduisent et passent `spirv-val`.
5. **Moteur Vulkan** : dispatchs directs et indirects (`svga-render/src/compute.rs`), dessins indirects, geometry shaders, tessellation (listes de patchs de 1 à 32 points), stream output (`VK_EXT_transform_feedback`, avec un compteur par tampon cible pour les ajouts et `DrawAuto`, rastérisation désactivable), dessins sans cible de rendu, descripteurs de stockage (tampons, images, tampons de texels) avec des ressources « nulles » à part pour les vues non liées, usage stockage pour les surfaces que Windows déclare liables en UAV (`SVGA3D_SURFACE_BIND_UAVIEW`), effacement des vues UAV.
6. **Côté serveur** : les objets de stream output dont les déclarations sont dans un MOB (`DX_DEFINE_STREAMOUTPUT_WITH_MOB`, `DX_BIND_STREAMOUTPUT`, relues à chaque dessin), les vues UAV (table d'objets, liaisons graphiques et compute), le stride des tampons structurés (`DEFINE_GB_SURFACE_V4`), la résolution des descripteurs commune aux dessins et aux dispatchs. `DX_SET_UA_VIEWS` donne les vues à partir de l'emplacement qui suit les cibles de rendu (`uavSpliceIndex`), comme le fait le pilote Mesa `svga`.
7. **Unigine Heaven 4.0 en Direct3D 11**, tessellation comprise (`guest/heaveneleven.cmd`), est le banc d'essai réel. Ses 184 shaders se traduisent et passent `spirv-val` ; il a fallu en plus les vues de profondeur et de stencil d'une surface D24S8 (`R24_UNORM_X8`, `X24_G8_UINT` : la vue prend le format stocké de l'image et l'aspect voulu), `ld_ms`, `resinfo` sur les textures multi-échantillonnées, et deux corrections de mélange. Les facteurs de mélange arrivent en `SVGA3dBlendOp`, dont les numéros diffèrent de `D3D10_BLEND` à partir de 12 (`BLENDFACTOR`, `SRC1COLOR`...) : le moteur les lisait comme `D3D10_BLEND`, et le brouillard de Heaven, qui multiplie la destination par sa seconde couleur, effaçait la scène. Le mélange à double source donne maintenant au `o1` du pixel shader l'emplacement 0, index 1. Pour trouver cette passe, `RSVGA_DUMP_TARGETS` (`rsvga-server/src/gpu/dump.rs`) enregistre en PNG les cibles de rendu de quelques images, les NaN en magenta, et journalise les passes plein écran avec leurs textures, leur shader et leur mélange.
8. **Le blocage de Heaven après 1 048 images : les résultats des requêtes.** Heaven se figeait toujours au même moment (1 044 images relues, journal détaillé ou non), rsvga au repos et l'invité tournant à vide. Le détecteur `watch` (`rsvga-server/src/watch.rs`, avec `RSVGA_PROFILE=1`) journalise un contexte DX qui se tait après beaucoup de travail, avec ses dernières commandes et l'état des files et des interruptions : tout était fini côté appareil, la dernière image se terminait normalement. Heaven crée une requête de statistiques du pipeline par image, et le pilote range leurs résultats dans un MOB de 102 400 octets : des cases de 92 octets, l'état (4 octets) puis le résultat (88 octets, `SVGADXPipelineStatisticsQueryResult`), 1 048 cases après une zone de travail et la barrière du contexte. rsvga écrivait les résultats dans la disposition des requêtes de Direct3D 9 (`SVGA3dQueryResult` : taille, état, résultat), l'état à +4. Le pilote lisait donc toujours « en attente », Heaven ne récupérait jamais ses résultats et gardait ses requêtes, et quand la file des cases fut pleine, le pilote attendit indéfiniment qu'une case se libère. Les requêtes DX s'écrivent maintenant comme le pilote Mesa `svga` les lit : l'état au début de la case, le résultat juste après. `d3dtest` a un test des requêtes (occultation, prédicat, horodatages, statistiques, événement, puis 1 200 requêtes de statistiques d'affilée) : 27 tests sur 27.
9. **Performances du chemin Direct3D 11** (Heaven, 1280×720, tessellation normale). Les 7 à 13 images par seconde notées d'abord étaient mesurées avec le journal détaillé ; sans lui, Heaven tournait à 29 images par seconde en moyenne (143 images relues par 5 s). `RSVGA_PROFILE=1` donne maintenant aussi le temps et le nombre de chaque commande (« profile commands »). Ce qui a compté, mesuré sur les mêmes deux minutes :
    - **Les tampons de relecture recyclés.** Chaque image que le pilote relit (le `READBACK_GB_SURFACE` qui suit chaque `PRESENTBLT`, 3,7 Mo) prenait un tampon neuf dans la mémoire de l'hôte, alloué puis touché page par page. Les tampons d'une soumission terminée sont maintenant gardés (64 Mo au plus) pour les copies suivantes. Avec le point suivant, la relecture passe de 6,1 à 3,7 ms.
    - **Une soumission anticipée quand le GPU n'a plus rien.** Tous les 64 dessins, si la dernière soumission est terminée, ce qui est enregistré part au GPU : il ne reste pas inactif en attendant le lot de 512.
    - **Un dessin moins cher.** Le moteur cherchait les modules de shaders avant même de savoir si le pipeline existait, rebâtissait la clé du pipeline et celle de l'échantillonneur dans des allocations neuves, recalculait la disposition des descripteurs, et renvoyait tous les états dynamiques et tous les tampons à chaque dessin. Il garde maintenant la clé, range les dispositions par shaders, et dans une même passe de rendu ne renvoie que ce qui change. Côté serveur, les variantes de shaders se retrouvent par l'adresse du code (comme en Direct3D 9) au lieu de hacher tout le programme. Enfin les tables chaudes (surfaces, vues, pipelines, objets des contextes) passent de SipHash à un hachage multiplicatif de quelques lignes (`svga-core/src/hash.rs`, celui du compilateur Rust) : les clés viennent de l'invité, qui pourrait au pire ralentir sa propre carte. Un dessin de Heaven passe de 5,7 à 3,3 µs (0,85 µs pour un dessin simple dans `draw_recording_speed`, le banc d'essai du moteur).
    - **Les mises à jour partielles de tampons vont droit au GPU.** Un `DX_BUFFER_UPDATE` sur un tampon que le GPU détient recréait une copie complète côté serveur, depuis le MOB, puis renvoyait le tampon entier au GPU au dessin suivant ; Heaven et DWM en font pour 8,6 Mo par image. La plage va maintenant du MOB à la mémoire d'envoi, puis au tampon du GPU.
    - **Résultat** : Heaven passe de 29 à 40 images par seconde en moyenne sur ses deux minutes (de 143 à 198–212 images relues par 5 s selon les mesures), son compteur montrant 31 à 55 selon les scènes. L'appareil est occupé 57 % du temps et le GPU 30 % : le reste se passe dans l'invité. Restent la relecture de chaque image (3,5 ms, que l'invité attend : le pilote recopie ensuite l'image dans la surface de DWM par des `DX_BUFFER_UPDATE` et des `DX_TRANSFER_FROM_BUFFER`), et 3,3 µs par dessin, pour environ 1 300 dessins par image.
10. **Pas encore** : compteurs des tampons append/consume, plusieurs flux de stream output, `switch` et sous-routines, doubles, `eval_*`, interfaces de classes ; les requêtes rendent des résultats fixes (un échantillon visible, des statistiques nulles).

## Questions ouvertes

- **Réglages `guestinfo.svga.wddm.*`** : le patch 0002 sait maintenant les servir, mais rsvga n'en fixe aucun ; le pilote prend ses défauts. Reste à savoir si certains méritent une valeur (VMware les prend dans le `.vmx`).
- **Curseur par MOB, ScreenDMA, IntraSurfaceCopy** (`CAP2_CURSOR_MOB`, `SCREENDMA_REG`, `INTRA_SURFACE_COPY`) : non annoncés pour l'instant. Le pilote garde le curseur par la FIFO, qui marche ; il écrit « cannot determine ScreenDMA support » sans conséquence visible en mode Display Only.
- **Plusieurs écrans** : les Tools annoncent `display_topology_set 2`. `DisplayTopology_Set` permettrait plusieurs fenêtres-écrans ; rsvga n'en montre qu'un pour l'instant.
- **Patchs QEMU à proposer upstream** : 0001 (accès non alignés vfio-user) et 0002 (port VMware), une fois le design validé par l'usage.
- **Affichage** : vfio-user ne transporte pas l'image vers la fenêtre de QEMU (`hw/vfio/display.c` appelle `ioctl` directement sur le fd du périphérique). En attendant, le serveur ouvre sa propre fenêtre et envoie clavier et souris par QMP. Cible : étendre le protocole vfio-user (GFX plane + dmabuf).
- **KVM `enable_vmware_backdoor=Y`** : activé sur cette machine pour les VMware Tools. Le paramètre est global au module `kvm` et ne change qu'au rechargement du module (toutes les VM arrêtées) ; le noyau 7.4 n'a pas de réglage par VM. La commande 75 vient du noyau de l'invité et passe sans ce réglage.
- **Niveau 11_1** : le pilote a les mêmes exigences de devcaps qu'en 11_0, mais Windows le refuse ; reste à trouver ce qui manque.
- **VMware Tools** (pilote invité) : logiciel propriétaire, téléchargé par l'utilisateur, jamais redistribué par ce projet.
